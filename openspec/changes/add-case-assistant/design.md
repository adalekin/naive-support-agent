# Design

## Context

Что делаем и зачем, описано в `proposal.md`, поведение в `specs/`. Здесь только факты, на которые опираются решения.

- Репозиторий пуст; соседний проект того же владельца с той же поставкой: сервер на Python 3.12, `uv`, `ruff`, `pytest`, SQLAlchemy 2 async, Alembic, `pydantic-settings`, `httpx[socks]`, `loguru` (github.com/adalekin/zrs, `server/pyproject.toml`).
- В соседнем проекте Telegram обёрнут шлюзом с типизированными событиями (`server/internal/service/telegram.py:78` того же репозитория, `TelegramGateway`), а реакция на событие вынесена в обработчики по типу события (`server/internal/service/bot.py:91`, `Handler[E]`) под слушателем обновлений (`bot.py:247`, `BotListener`).
- Обновления Telegram приходят либо через `getUpdates` с длинным опросом, либо через вебхук, одно из двух; неподтверждённые обновления хранятся до 24 часов, подтверждением служит следующий `offset` (core.telegram.org/bots/api, раздел Getting updates).
- В режиме приватности бот в группе получает только команды, ответы на свои сообщения и служебные сообщения; все сообщения получает бот с выключенным режимом приватности или бот-администратор; выключение действует после повторного добавления в группу (core.telegram.org/bots/features, Privacy Mode).
- Реакции на сообщения (`message_reaction`) бот получает, только если он администратор чата и явно перечислил этот тип в `allowed_updates` (core.telegram.org/bots/api, Update).
- Сообщение от имени чата несёт `sender_chat`, а в `from` в этом случае фиктивный пользователь (core.telegram.org/bots/api, Message).
- `/setprivacy` в BotFather переключает режим приватности, `/setjoingroups` запрещает добавлять бота в группы (core.telegram.org/bots/features, BotFather commands).
- Номер пользователя и чата в Telegram укладывается в 52 значащих бита, хранить его надо 64-битным целым (core.telegram.org/bots/api, User и Chat).
- Скрытый текст задаётся сущностью `spoiler`, у отправляемых фото и видео есть признак `has_spoiler` (core.telegram.org/bots/api, MessageEntity и sendPhoto).
- Вход по коду устройства (OAuth 2.0 Device Authorization Grant, RFC 8628): приложение получает от провайдера код устройства и код для человека, человек вводит код на странице провайдера, приложение опрашивает провайдера и получает токены. Провайдер среды разработки включает его для клиента одной настройкой и показывает страницу ввода сам (keycloak.org/docs, Server Administration Guide, Device authorization grant).
- У провайдера среды разработки обычный refresh token живёт не дольше пользовательской сессии, по умолчанию SSO Session Max 10 часов; offline token, выданный по `scope=offline_access`, не подчиняется SSO Session Idle и Max и действует, пока им пользуются хотя бы раз за Offline Session Idle (по умолчанию 30 дней); для него у пользователя нужна роль `offline_access`; при включённом Revoke Refresh Token каждый токен используется один раз и после обновления хранится новый (keycloak.org/docs, Server Administration Guide, Session and token timeouts и Offline access).
- Keycloak 26.8 (образ из `compose.yaml`): после отключения учётной записи обновление offline token отклоняется с `invalid_grant` и описанием «User disabled»; после снятия роли клиента следующий access token приходит без неё; после повторного включения учётной записи тот же offline token снова обновляется; вход по коду устройства проходит и у человека без роли клиента (проверка задачи 5.1).
- Что провайдер отвечает на обновление токена после отключения учётной записи или снятия роли, в документации провайдера среды разработки не описано.
- Claude Agent SDK это Claude Code в виде библиотеки со встроенными инструментами Read, Write, Edit, Bash, WebSearch, WebFetch; Tool Runner из `anthropic` гоняет цикл только по инструментам, которые объявило приложение (скилл claude-api, раздел Building an Agent).
- На Claude Opus 5.5 блоки рассуждений привязаны к модели и разговору: правка уже отправленной истории ломает их, поэтому история разговора с моделью должна только дописываться; серверное сжатие контекста правкой истории не считается (скилл claude-api, `shared/model-migration.md`, Breaking change 3).
- В примерах скилла структурированный ответ (`output_config.format`) показан на `messages.create`, а сочетание с Tool Runner не показано (скилл claude-api, `python/claude-api/tool-use.md`).
- Сервис ставится в сеть организации рядом с её источниками и подключается к ним с доступом только на чтение (`proposal.md`, Impact); открывать источники наружу ради ассистента не предполагается.

## Goals / Non-Goals

Цели и то, что не делаем, перечислены в `proposal.md`. Дизайн добавляет одно ограничение: каждое требование «ассистент не может…» держится на устройстве программы, а не на том, что модель послушается инструкции.

## Decisions

### 1. Цикл агента: Messages API и Tool Runner, только свои инструменты

Ассистент вызывает модель через `anthropic` (`client.beta.messages.tool_runner`), и в запросе есть только инструменты, которые объявил сам сервис. Модель физически не может выполнить действие, для которого нет инструмента; набор инструментов и есть граница «только информация и советы».

Модель задаётся настройкой установки без значения по умолчанию; в примере настроек стоит `claude-opus-5-5` с серверными запасными моделями (`fallbacks: "default"`) на случай отказа классификатора. Уровень усилия тоже настройка.

Отвергнуто:
- Claude Agent SDK: приносит Bash, Write, WebFetch и файловую систему контейнера; чтобы доказать «только чтение», пришлось бы отключать и проверять каждый встроенный инструмент, а Bash в контейнере с доступом к базе снимает границу целиком.
- Managed Agents: цикл и песочница у Anthropic, а источники организации доступны только изнутри её сети; открывать базу наружу ради ассистента нельзя.
- Свой цикл без Tool Runner: та же функциональность, больше своего кода; хуки Tool Runner покрывают журнал и перехват ошибок.

### 2. Шлюз источников: Proxy над адаптерами источников

Модель видит один набор инструментов, а за ним стоит `SourceGateway`. Это Proxy: он проверяет, что инструмент разрешён установкой, снимает метки с аргументов, вызывает источник, маскирует результат, пишет вызов в журнал. Каждый вид источника это Adapter с общим интерфейсом `Source` (`list_tools`, `call`), зарегистрированный в `SourceRegistry` (Registry) по виду из настроек:

- `McpSource`: внешний MCP-сервер установки (stdio или HTTP) через клиент `mcp`; установка перечисляет, какие его инструменты разрешены. Так подключаются база, журналы, ошибки, трекер задач, интерфейс продукта.
- `RepositorySource`: чтение кода из клона репозитория: поиск и чтение файла, без записи и без запуска.
- `AttachmentSource`: вложения обращения, скачанные через Bot API; видео разбирается на кадры.

Запрет записи держится на трёх уровнях, каждый сам по себе: установка выдаёт доступ только на чтение; шлюз пропускает только инструменты из списка установки; у адаптеров нет методов записи.

Отвергнуто:
- MCP-коннектор Messages API (`mcp_servers` в запросе): сервер должен быть доступен Anthropic по публичному адресу, а источники доступны только изнутри сети организации.
- Один инструмент «выполни SQL» поверх пишущего пользователя с запретом в промпте: запрет держится на послушании модели.
- Ветвление `if kind == "postgres" …` в коде агента вместо адаптеров: каждый новый источник менял бы цикл.

### 3. Псевдонимизация: карта меток кейса и Decorator над шлюзом

`Pseudonymizer` держит у каждого кейса `LabelMap` (Value Object: метка ↔ значение). На входе он заменяет почты и телефоны по шаблону в любом тексте, а имена и платёжные данные по списку полей источников из настроек. На выходе к модели идут только метки; аргументы инструментов распаковываются обратно перед вызовом источника. `TelegramRenderer` подставляет значения в ответ и оборачивает их сущностью `spoiler`. Карта хранится вместе с кейсом, чтобы уточнения в ветке получали те же метки.

Отвергнуто: маскировать только сообщение сотрудника. Почта клиента пришла бы модели в первом же ответе базы.

### 4. Доступ: привязка по коду устройства и проверка обновлением токена

`StaffBinding` (Aggregate): номер аккаунта Telegram, `sub` учётной записи, offline token в зашифрованном виде, время привязки. Вход запрашивает `scope=offline_access`: обычный refresh token кончился бы вместе с сессией через несколько часов (Context), и сотрудники каждое утро входили бы заново. Уникальны и номер Telegram, и `sub`: новая привязка учётной записи удаляет прежнюю в той же транзакции.

`DeviceLogin` (Process Manager) ведёт вход: запрашивает у провайдера коды, хранит код устройства и срок, опрашивает провайдера с интервалом, который тот вернул, и по результату создаёт привязку или сообщает об отказе. На один аккаунт Telegram действует один незавершённый вход.

`AccessGuard` при каждом обращении обменивает offline token на новые токены, сохраняет новый offline token, если провайдер его выдал, и читает роли из access token по месту, заданному установкой. Обновления одной привязки идут по очереди, чтобы два параллельных сообщения не израсходовали один токен. Отказ провайдера (учётная запись отключена, сессия отозвана) удаляет привязку; недоступность провайдера даёт отказ в разборе с сообщением сотруднику. Ответственные определяются так же: привязанные люди, у которых при проверке есть роль ответственного.

Адаптер провайдера знает только OpenID Connect: адреса берутся из документа обнаружения (`.well-known/openid-configuration`), ничего специфичного для конкретного поставщика в коде нет.

Отвергнуто:
- Admin API провайдера через служебную учётную запись: привязывает код к одному продукту, а настройки проекта запрещают ветвление под поставщика.
- Кэш ролей на время: спека требует проверки при каждом обращении.
- Одноразовая ссылка из веб-интерфейса, как в соседнем проекте: у ассистента нет веб-интерфейса, и пришлось бы открывать входящий адрес.

### 5. Telegram: длинный опрос, фильтр обновлений, обработчики по типу события

`TelegramGateway` повторяет шлюз соседнего проекта (`telegram.py:78`): `httpx`, выход через прокси из настроек, типизированные события. Обновления читаются длинным опросом; входящего адреса у сервиса нет.

Режим приватности выключен: без этого бот не видит упоминаний себя и ответственного (Privacy Mode). Поэтому до любой записи обновление проходит `UpdateFilter`, цепочку проверок (Chain of Responsibility, каждая проверка это Specification): группа из списка установки, нет `sender_chat`, есть привязка с ролью, сообщение относится к ассистенту (личка, упоминание ассистента, упоминание ответственного с кейсом, ответ в ветке кейса). Обычная переписка группы, не адресованная ассистенту, отбрасывается без следа. В журнал попадает только обращение к ассистенту (личка, упоминание ассистента, упоминание ответственного с кейсом) от человека без доступа, и только номера аккаунта и чата, без текста.

Добавление в группу не из списка (`my_chat_member`) вызывает `leaveChat`. Оценку ответа ставят кнопками под ответом (`callback_query`): реакции требуют прав администратора (Update, `message_reaction`), а давать боту права администратора в группах незачем.

Обработчики событий повторяют `Handler[E]` соседнего проекта (`bot.py:91`): `HandleCaseMessage`, `HandleFeedback`, `HandleMembership`, `HandleDirectLogin`. Номер последнего обработанного обновления хранится в базе (Idempotent Receiver): после перезапуска обновление не обрабатывается дважды.

### 6. Кейс и сбой: агрегаты, репозитории, единица работы

- `Case` (Aggregate): ключ ветки (номер чата и корневого сообщения), сотрудник, клиент (метка и подтверждённый номер учётной записи), состояние (`investigating`, `waiting_client`, `waiting_fix`, `waiting_owner`, `resolved`), условие ожидания, история разговора с моделью, `LabelMap`, ссылка на `Incident`.
- `Incident` (Aggregate): ключ причины, описание, время эскалации, связанные кейсы.
- `JournalEntry`: запись журнала, только дописывается.

Доступ к ним через репозитории на SQLAlchemy, транзакция на одно событие (Unit of Work), как в соседнем проекте. История разговора с моделью только дописывается: так требуют блоки рассуждений (Context). Когда запрос хода перерастает 150 тысяч входных токенов, после хода модели включается серверное сжатие контекста (`compact_before_next_turn`): сводка заменяет историю кейса и на сервере, и в базе ассистента, следующий ход начинается со сводки.

- `CaseTurn`: ход кейса, который ждёт модели (сообщение сотрудника, ответ ответственного, проверка по расписанию). Слушатель Telegram только принимает обращение и кладёт ход в базу в транзакции обновления; ход переживает перезапуск.
- `CaseMessage`: сообщение ветки кейса с его ролью (обращение, ответ, вопрос «что не так», прочее); ответ на любое из них продолжает кейс.

Кейсы одного чата обрабатываются параллельно, а ходы одного кейса по очереди: воркер берёт ходы кейса по одному в порядке поступления. Подтверждение «взялся» уходит до вызова модели.

Ход кейса идёт минуты, поэтому ни одна строка не держится заблокированной всё это время: кейс живёт в памяти хода и сохраняется одной короткой транзакцией в конце, а каждая команда ассистента открывает свою короткую единицу работы. Иначе проверка доступа в слушателе ждала бы окончания чужого разбора.

Переписка с моделью, карта меток и содержимое хода (текст сотрудника и клиента как есть, номера файлов) хранятся зашифрованными тем же ключом установки, что и offline token: в них настоящие почты, телефоны, имена и картинки клиента. Шифрует тип столбца (`EncryptedJson`, Fernet), так что код, который работает с кейсом, видит обычные структуры. Смена ключа делает старые кейсы нечитаемыми, как и привязки.

`RetentionSweeper` раз в час удаляет кейсы, по которым не было хода дольше срока установки, вместе с ветками и ходами; записи журнала остаются со ссылкой на кейс, сброшенной в пусто. Ход по расписанию тоже ход, поэтому кейс, который ждёт исправления, не удаляется.

Отвергнуто:
- История кейса только в ветке Telegram: Bot API не отдаёт историю чата, а у модели нет сохранённых блоков рассуждений, которые надо передавать обратно неизменными.
- Сессии в памяти процесса: теряются при перезапуске, а кейс ждёт исправления днями.

### 7. Свои инструменты ассистента: Command над агрегатами

Кроме источников модель получает инструменты, которые меняют только состояние самого ассистента: `set_case_state`, `link_incident`, `escalate`, `propose_rule`, `identify_client`. Каждый это Command с проверкой входа: `escalate` по открытому `Incident` не зовёт ответственного второй раз, `identify_client` принимает только учётную запись, найденную в источниках по примете из кейса. Ни один из них не обращается к системам организации.

Ответ сотруднику модель отдаёт строгим инструментом `submit_answer` (`strict: true`): части ответа из `case-answer`, вложения для пересылки. Сочетание `output_config.format` с Tool Runner не подтверждено (Context), а строгий инструмент даёт ту же проверку схемы внутри цикла. `TelegramRenderer` собирает из ответа сообщение с сущностями `spoiler` и кнопками оценки.

Отвергнуто: определять состояние кейса и эскалацию разбором свободного текста ответа модели. Формулировка меняется от ответа к ответу, а команда с проверкой входа либо выполнена, либо отклонена.

### 8. Сопровождение кейсов: Process Manager по расписанию

`FollowUpScheduler` раз в интервал из настроек берёт кейсы в `waiting_fix` и для каждого вызывает модель с узкой задачей: проверить по источникам, выполнено ли условие ожидания. При выполнении пишет в ветку кейса и меняет состояние. Сводка для ответственного считается запросом к журналу, без модели.

Отвергнуто: подписка на события выкатов. Источники выкатов у установок разные, а общий для всех установок путь только через инструменты, которые она подключила.

### 9. Инструкции установки: каталог файлов, загрузка при старте

Установка монтирует каталог: инструкции разбора, описание источников, правила компенсаций, список полей с персональными данными. `InstructionSet` загружается при старте и проверяется; без каталога или с пустыми инструкциями процесс не стартует. Текст инструкций идёт в начало системного промпта и не меняется между запросами, чтобы работало кэширование промпта.

Отвергнуто: инструкции в базе ассистента с правкой через бота. Ассистент не меняет инструкции (`escalation`, предложение правила), а каталог из приватного репозитория установки даёт историю и ревью правок.

### Переработка существующего кода

Существующего кода нет. Шлюз Telegram и шаблон обработчиков переносятся из соседнего проекта как образец, а не общей библиотекой: у двух проектов разные события и разный выход наружу, общая библиотека связала бы их выпуски. Оставлено как есть: ни один файл соседнего проекта не меняется.

### Поставка

Один Docker-образ, Helm-чарт в `deploy/helm`, публикация образа и чарта в GHCR по тегу, как у соседнего проекта. Миграции базы Job чарта. Установка в конкретный кластер, бот в BotFather, клиент у провайдера и пользователи источников делаются вне этого репозитория.

Порядок подготовки бота, который README описывает для установки: выключить режим приватности (`/setprivacy`), добавить бота во внутренние группы, затем запретить добавление в группы (`/setjoingroups`). После этого бота нельзя добавить никуда, а выход из чужих групп остаётся второй защитой.

## Risks / Trade-offs

- [Risk] Бот с выключенным режимом приватности получает всю переписку разрешённых групп → текст отклонённых обновлений не сохраняется и не попадает в журнал; в список групп входят только внутренние группы без клиентов (`installation-settings`).
- [Risk] Утечка токена бота даёт чтение его переписки → токен только в Secret, в журнал и ответы не пишется (`installation-settings`).
- [Risk] Утечка базы ассистента даёт offline token сотрудников, которые живут неделями → токены зашифрованы ключом из Secret; привязка снимается при отказе провайдера; установка может включить Revoke Refresh Token, и украденный токен станет бесполезен после первого же обновления ассистентом.
- [Risk] Учётную запись отключили и снова включили, и тот же offline token опять обновляется (Context) → если за время отключения сотрудник обратился к ассистенту, привязка удалена при отказе провайдера и Telegram привязывается заново; если не обращался, привязка продолжает действовать: включённая учётная запись снова получает доступ, и это принятое поведение.
- [Risk] Сотрудника уговорили подтвердить чужой код → короткий срок кода, сообщение о каждой привязке в рабочих группах.
- [Risk] Инструменты интерфейса продукта умеют нажимать кнопки, запрет оплаты держится на учётной записи → у тестовой учётной записи нет средств и способов оплаты; установка не даёт ей прав администратора.
- [Risk] Внешний MCP-сервер может объявить инструмент записи под безобидным именем → шлюз пропускает только инструменты, перечисленные установкой; доступ сервера к источнику только на чтение.
- [Risk] Указание в тексте клиента или в данных → границы доступа держатся на шлюзе и `identify_client`, а не на промпте; текст клиента передаётся модели как данные пользователя, а не как системная инструкция.
- [Risk] Имена и платёжные данные в свободном тексте уходят модели → в спеке это записано как поведение; закрыть полностью без распознавания текста нельзя.
- [Risk] Стоимость: каждый кейс это цикл модели с инструментами, сопровождение добавляет вызовы по расписанию → бюджет токенов на разбор кейса и интервал сопровождения задаются установкой; расход по кейсам пишется в журнал.
